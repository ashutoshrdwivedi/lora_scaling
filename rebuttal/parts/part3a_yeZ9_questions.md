We thank the reviewer for an exceptionally thorough review. New experiments address Q1, Q3, Q4 and Q5 with measurements; the cross-model table is in the general response.

**Q1 (end-to-end latency).** Our reported latency is already end-to-end, not GPU-only: it includes CPU batch assembly (the per-sample LoRA gather) plus the full GPU forward including the batched head, and Finding 5 decomposes the two. We have since instrumented the one remaining step, **result scatter** (per-tenant logit slicing + softmax): a single $O(B \cdot c_{\max})$ tensor-indexing operation costing 0.13–1.63 ms on bge-m3, i.e. **0.8–1.2% of end-to-end latency**, so the whole request path is now accounted for. Beyond the process boundary — queueing, dynamic batching — we describe the architecture (Appendix C) but do not benchmark it.

**Q2 (memory at 47,000 adapters; KV-cache headroom).** First: **encoders have no KV cache.** The forward is one non-autoregressive pass, so nothing persists across tokens and sequence length affects only transient activations, freed per batch. What scales with tenant count is the resident adapter store: $2MLdr$ values, i.e. at $r{=}8$ fp16, 1.57 MB for bge-m3 and 5.90 MB for XLM-R-XL. The 47,000-adapter store is therefore 68.8 GB, and Finding 4's ceiling is precisely that store filling the A100's 80 GB alongside base weights and activations.

On headroom, a direct measurement: on XLM-R-XL at 11,000 resident adapters, peak memory moves only from 73.5 GB to 74.5 GB as batch size goes 8 → 128. **A 16× increase in serving load costs 1.0 GB.** The tenant ceiling is set by adapter geometry and is essentially independent of the load running against it — a predictable capacity number, not one re-derived per deployment.

**Q3 (mitigating the CPU ceiling).** It is not a hard ceiling. The GPU-resident `index_select` assembler sketched in our Limitations is now implemented and measured in pure PyTorch. On all-MiniLM-L6-v2, CPU-bound by design, it lifts single-stream throughput from 6,804 to 15,342 samples/s, cuts assembly share from 50–58% to 1.8–4.1% at $B \geq 64$, and removes the tail spike (p99/p50 from 5.14× to 1.01×). On bge-m3 it gives 1.17–1.51×. This is a per-replica compute bound, not a load-tested QPS figure. The paper's numbers use the baseline assembler and are therefore conservative.

**Q4 (beyond BERT/RoBERTa).** Yes — three new encoders run the same decomposition with no architecture-specific kernels: ELECTRA-large (334M) in our native engine, plus DeBERTa-v2-xlarge (885M, disentangled attention) and XLM-RoBERTa-XL (3.5B, 36 layers) via a generic HuggingFace hook wrapper injecting the batched LoRA path into the stock forward. The $O(1)$-in-$N$ latency and the PEFT-mixed speedups replicate on all of them (general-response table). Parity: the wrapper *mechanism* is unit-tested against PEFT on BERT, ELECTRA and DeBERTa-v2; XLM-R-XL has no dedicated parity test, so the verified claim is about the attachment path, not that checkpoint individually.

**Q5 (mixed ranks in one batch).** Pad-to-max overhead is exactly the cost of running a batch at its maximum rank, and Finding 3 measures that as latency-neutral. Padding inflates only the delta path $B_i A_i x$; the shared base path is rank-independent and dominates — at $r \ll d$ the delta adds $2r/d$ of one projection's arithmetic, 1.56% at $r{=}8$, 6.25% at $r{=}32$. Finding 3 sweeps the *uniform* batch rank over $r \in \{4, 8, 16, 32\}$ — precisely the pad-to-max worst case: p50 moves 40.41 → 39.93 ms (1.19%, within seed noise), replicating within 2.46% on all four new configurations. In the current implementation an `AdapterStore` is rank-homogeneous, so a mixed-rank fleet is served today by one store per rank with rank-bucketed batching: zero padding, no kernel changes. The real cost of higher rank is memory: doubling $r$ halves the tenant ceiling (47,000 → 23,500 → 11,750, Finding 4). We will reword the Limitations: "wasting compute" overstates it; the trade-off is tenant density versus rank.

**Q6 (registration share under churn).** In our system this is $\approx 0$ by construction, independent of pool size. Registration is a single `AdapterStore` insertion — a memcpy of the A/B factors and head — measured at 0.29 ms/adapter, flat in $N$. Serving requests never register or swap; they select resident adapters by index — the $O(1)$ gather already counted in assembly. Replacing the entire 1,000-adapter pool hourly costs 0.29 s against 3,600 s, i.e. **0.008% of wall-clock**, off the serving path. The contrast: PEFT's `add_adapter` rescans per-layer `ModuleDict`s on every call, so total add time grows quadratically — 14.2 s for 100 adapters versus 1,229.2 s for 1,000 — putting the marginal add at $N{=}1000$ near 2.5 s, some 8,500× ours. We measure the per-add cost and the scaling directly; an interleaved add-under-load microbenchmark is a camera-ready addition.
