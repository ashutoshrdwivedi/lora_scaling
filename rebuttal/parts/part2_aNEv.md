We thank the reviewer for the assessment and address both concerns.

**"Implementation optimization, not algorithmic innovation."** We accept the characterization of the artifact and would offer a reframing of the claim. What we contribute is not a code path but an observation with a measured consequence: encoder inference is *base-dominated*, so per-tenant adaptation can be decomposed as $W_0 x + B_i A_i x$ with the base path shared across a mixed-tenant batch, making serving cost $O(1)$ in tenant count **by construction** rather than by tuning.

The evidence that this is the operative mechanism, not a happy accident, is an ablation: running the identical batch with the entire LoRA path disabled — gather, shrink/expand and merge — changes wall-clock by **2.4 ms of 26.4 ms, or 9.0%**. That is also what makes the negative result in Finding 6 sharp: a custom fused kernel can only touch that path, so 9.0% bounds what any kernel could recover. It cannot beat deleting the work. This explains *why* the decoder-side literature needs custom CUDA and encoders do not, and it predicts where the approach stops paying rather than only where it wins.

The new experiments **tighten** that bound instead of leaving it untested. The analytic FLOP ratio $3d/r$ grows with width — 384 at $d{=}1024$, 576 at $d{=}1536$, 960 at $d{=}2560$ — so the maximum recoverable FLOP share falls from 0.26% to 0.17% to 0.10%. The case for custom kernels gets *weaker* as encoders get larger, which is the opposite of the decoder-side trend that motivates them. And the mechanism now has support across four encoder families, two GPU classes, and a 10× span of model sizes (334M → 3.5B): the same code reproduces the paper's results on all of them (general-response table).

We would add that the deployment gap is real and currently unclosed: vLLM's LoRA-pooling path covers only decoder-backbone embedders, and PEFT's mixed-batch API degrades 5.6–21.2× at our operating points while registering adapters in $O(N^2)$ cumulative time.

**Adoption by the open-source community.** We agree this cannot be claimed in advance, and we think the honest response is to lower the barrier rather than argue about it. The benchmark repository is already public (anonymized), and since submission we have added a generic HuggingFace attachment path so that applying the method to a new encoder needs no model-specific code. At camera-ready we will release the serving path as a pip-installable library.

**Future directions**, as requested: (i) a masked-BMM variant so one batch can mix ranks and target-module sets without padding; (ii) fixed-capacity slotting so the packed GPU-resident assembler also supports incremental registration at $O(1)$; (iii) quantitative evaluation of the replicated multi-GPU architecture of Appendix C; (iv) extending the decomposition to decoder-backbone embedding models; and (v) extending per-tenant adaptation to architectures with batch-shared projections — e.g. DeBERTa-v2's relative-position path, which our current decomposition cannot target because that projection has no per-sample counterpart.
