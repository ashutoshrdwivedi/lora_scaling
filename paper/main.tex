\begin{abstract}
We introduce \sysname, a system for serving thousands of independently
fine-tuned LoRA adapters on a single shared encoder model in a single GPU
forward pass.
Personalizing an NLP feature (e.g.\ text classification) for thousands of
customers traditionally required one fine-tuned model per customer.
LoRA \cite{hu2022lora} eliminated the \emph{storage} barrier by reducing
per-customer state to a few hundred kilobytes; the remaining barrier is
\emph{serving}---batching requests across customers without merging adapter
weights into the base model.
\sysname{} avoids weight merging by computing the base projection
$W_0 x$ and the per-tenant LoRA delta $\Delta W_i x = B_i A_i x$ separately,
then fusing them additively---enabling heterogeneous adapters and per-tenant
logistic-regression heads to be batched via \texttt{torch.bmm} with
pre-allocated GPU buffers, requiring no custom CUDA kernels.
On a single NVIDIA A100-40GB GPU with \texttt{BAAI/bge-m3} as the base
model, \sysname{} serves \textbf{20{,}000 pre-loaded LoRA adapters at 800
samples/sec} with 40~ms p99 latency at batch size 32, and scales from 100 to
20{,}000 adapters with statistically unchanged latency---empirically confirming
$\mathcal{O}(1)$ scaling in adapter count.
Against the HuggingFace PEFT per-request swap baseline on the same hardware,
\sysname{} delivers a \textbf{33--571$\times$ throughput improvement}
(growing with both batch size and adapter pool size) and a
\textbf{$>$600$\times$ improvement in cold-start deployment time}.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Deploying a personalized NLP feature---such as text classification---to
thousands of customers is a storage and compute challenge.
Maintaining a fully fine-tuned model per customer is infeasible:
at $\approx$1.1~GB per copy in float16, serving 20{,}000 customers would require
over 22~TB of model weights.
LoRA \cite{hu2022lora} resolves the \emph{storage} problem: by expressing
each customer's adaptation as a low-rank update to a single shared base
encoder, the per-customer footprint shrinks to $\approx$1.6~MB (rank~8,
24 layers)---a $\approx$700$\times$ reduction.
The remaining challenge is \textbf{inference}: how to serve thousands of
different LoRA adapters simultaneously on one GPU, at low latency, in batched
mixed-tenant requests.

Existing multi-tenant LoRA serving systems---Punica \cite{chen2024punica},
S-LoRA \cite{sheng2024slora}, vLLM \cite{kwon2023vllm}, and LoRAX
\cite{predibase2023lorax}---target autoregressive decoder workloads, where
custom CUDA kernels and paged-memory pools are needed for token-by-token
generation over a KV cache. Encoders are structurally different: the
bidirectional forward pass at sequence length $S \gg 1$ is compute-bound
and dominated by base-model projections, so the LoRA path lends itself to
standard batched matrix multiplication rather than custom kernels.
Heterogeneous-adapter batching for encoder models is, to our knowledge,
not yet supported by released runtimes (\S\ref{sec:relwork}).

We present \sysname, a serving system that fills this gap.
The core design principle is \textbf{late fusion}: rather than merging a
tenant's LoRA weights into the base model (which serializes batching),
\sysname{} decomposes each projection into a shared base path
$W_0 x$ and a per-sample LoRA delta $B_i A_i x$, computing both
independently and summing the results.
This decomposition enables an entire mixed-tenant batch to be processed in

\section{Background}
\label{sec:background}

\subsection{LoRA for Encoder Models}
\label{sec:background_lora}

LoRA \cite{hu2022lora} decomposes a weight update $\Delta W \in
\mathbb{R}^{d \times d}$ as the product of two low-rank matrices:
\begin{equation}
  \Delta W = B A, \quad
  A \in \mathbb{R}^{r \times d},\;
  B \in \mathbb{R}^{d \times r},\;
  r \ll d.
\end{equation}
The full forward pass for a single sample becomes
$h = W_0 x + \frac{\alpha}{r} B A x$,
where $W_0$ is the frozen pre-trained weight and $\alpha$ is a scaling
hyperparameter typically set equal to $r$.
For an encoder of hidden size $d = 384$ with $L = 12$ layers, applying LoRA
% * <Ashutosh Dwivedi> 17:56:16 26 May 2026 UTC+0530:
% Use the numbers for BGE M3 model
at rank $r = 8$ to the query and value projections yields
$2 L \cdot (d r + r d) = 147{,}456$ trainable parameters per adapter---a
$24\times$ reduction over full fine-tuning of those layers.
% * <Ashutosh Dwivedi> 17:55:45 26 May 2026 UTC+0530:
% verify the multiplier

In this work, $B$ is initialized to zero so that $\Delta W = 0$ at the start
of training, leaving the pre-trained representations intact.

\subsection{The Multi-Tenant Serving Problem}
\label{sec:background_serving}

Consider a service that exposes a single classification feature to $N$
customers, where each customer gets a fine-tuned
\texttt{BAAI/bge-m3} \cite{chen2024bge} on their own labeled
data to specialize the feature to their domain.
Without LoRA, three naive serving strategies all fail at scale:

\paragraph{One model per tenant.}
Storing $N$ full model copies requires $N \times 1.1$~GB in float16.
At $N = 20{,}000$ that is $\approx$22~TB---the equivalent of over 275
NVIDIA A100-80GB GPUs dedicated to weight storage alone.
Moreover, cross-tenant batching is impossible: different model instances
cannot share a forward pass.

\paragraph{Weight merging per request.}
Load one base model; before each request, compute $W' = W_0 + B_i A_i$
in-place, run inference, then restore $W_0$.
This approach has several fatal flaws: (i) the merge-restore cycle is
\emph{serial}, blocking all other requests during weight mutation;
(ii) in-place CUDA tensor modifications cause memory fragmentation and
out-of-memory crashes under load; (iii) a crash between merge and restore
contaminates subsequent tenants' requests with the wrong adapter---a
correctness and security failure.

\paragraph{Sequential single-tenant batching.}
Serve all requests for tenant $i$ as a batch, then switch adapters for
tenant $i+1$.
Cross-tenant requests cannot be batched, so average GPU utilization
approaches $1/N$---near zero for large $N$.

The right solution batches \emph{heterogeneous} adapters in a single forward
pass, which requires a decomposition where different linear operations can be
applied per sample without serialization.

\subsection{Late-Fusion Decomposition}
\label{sec:lf_decomp}

The core insight is that the LoRA forward pass
$h = W_0 x + B_i A_i x$
can be split into two \emph{independent} computations:
\begin{align}
  h_{\text{base}} &= W_0 x \label{eq:base} \\
  h_{\text{delta}} &= B_i (A_i x) \label{eq:delta} \\
  h &= h_{\text{base}} + h_{\text{delta}} \label{eq:fuse}
\end{align}

Equation~\ref{eq:base} uses the same frozen $W_0$ for every sample in the
batch and is computed by standard PyTorch linear layers.
Equation~\ref{eq:delta} applies a \emph{different} $(A_i, B_i)$ pair to each
sample $i$, which requires batched matrix multiplication rather than a
broadcast multiply.
Equation~\ref{eq:fuse} is a zero-allocation element-wise addition.

For a batch of $\mathcal{B}$ samples with hidden size $H$ and sequence length $S$:
\begin{align}
  h_{\text{shrink}} &= \texttt{bmm}(x,\; [A_0,\ldots,A_{\mathcal{B}-1}])
    \in \mathbb{R}^{\mathcal{B} \times S \times r} \label{eq:shrink} \\
  h_{\text{delta}} &= \texttt{bmm}(h_{\text{shrink}},\; [B_0,\ldots,B_{\mathcal{B}-1}])
    \in \mathbb{R}^{\mathcal{B} \times S \times H} \label{eq:expand}
\end{align}

\noindent
where $[A_0, \ldots, A_{\mathcal{B}-1}] \in \mathbb{R}^{\mathcal{B} \times H \times r}$ is the
stack of per-sample shrink matrices, assembled from the adapter store at
request time.
Both \texttt{bmm} calls are a single GPU kernel launch, processing all $\mathcal{B}$
samples simultaneously regardless of how many distinct adapters they reference.

This decomposition contrasts with the SGMV kernel used in Punica
\cite{chen2024punica} along three axes.
First, \emph{segmentation}: SGMV groups inputs by LoRA model ID
(``We group inputs to the same LoRA model consecutively'' \cite{chen2024punica})
and dispatches one thread-block per adapter group; \texttt{torch.bmm}
applies a different $(A_i, B_i)$ to every batch item with no grouping.
Second, \emph{operand shape}: SGMV operates on vector inputs $(1, H)$
optimized for the autoregressive decode shape;
\texttt{bmm} operates on the matrix shape $(S, H)$ native to encoder prefill.

compiled against a specific CUDA version; \texttt{bmm} ships with PyTorch
and runs anywhere PyTorch runs.

\subsection{Batched Classification Heads}
\label{sec:lr_head}

In the multi-tenant classification setting, each tenant trains a
% * <Ashutosh Dwivedi> 18:21:21 26 May 2026 UTC+0530:
% Kehsav : 1.⁠ ⁠Should we talk about Logistic Regression head or avoid it ?
logistic-regression (LR) head on top of the encoder's pooled
\texttt{[CLS]} representation.
Tenants differ in the number of output classes: tenant $i$ may have $c_i$
classes where $c_i$ varies from 2 to over 100.

\sysname{} serves all heads in a single BMM call.
Given a batch of pooled representations
$p \in \mathbb{R}^{\mathcal{B} \times 1 \times H}$
and per-tenant weight matrices
$W^{\text{cls}}_i \in \mathbb{R}^{c_i \times H}$ and bias vectors
$b^{\text{cls}}_i \in \mathbb{R}^{c_i}$,
we zero-pad all weight matrices to the maximum label count
$c_{\max} = \max_i c_i$ in the batch and form a stacked tensor
$W^{\text{cls}} \in \mathbb{R}^{\mathcal{B} \times c_{\max} \times H}$.
The logit computation is:
\begin{equation}
  \text{logits} = \texttt{bmm}(p,\; {W^{\text{cls}}}^\top) + b^{\text{cls}}
  \;\in\; \mathbb{R}^{\mathcal{B} \times 1 \times c_{\max}}
\end{equation}

Callers slice $[:, :, :c_i]$ per sample before applying softmax.
The zero-padded columns contribute zero gradient and do not affect the
probability distribution of any tenant.

\subsection{Pre-Allocated GPU Buffers}
\label{sec:buffers}

Without explicit buffer management, \texttt{torch.bmm} allocates a new output
tensor on every call.
For a 24-layer encoder with target modules $\{\text{query}, \text{value}\}$,
this produces $2 \times 2 \times 24 = 96$ CUDA allocations per forward pass.
Each allocation invokes the CUDA caching allocator, which searches for a free
contiguous block at a cost on the order of microseconds per call---adding up to
several hundred microseconds of pure allocator overhead per batch.
% TODO: restore (\S\ref{sec:ablation}) cross-ref once §4.6 is restored.

\sysname{} pre-allocates two fixed-size buffers at initialization:
\begin{align}
  \mathtt{out\_A} &\in \mathbb{R}^{\mathcal{B}_{\max} \times S_{\max} \times r} \\
  \mathtt{out\_B} &\in \mathbb{R}^{\mathcal{B}_{\max} \times S_{\max} \times H}
\end{align}
and passes them via the \texttt{out=} argument of every \texttt{bmm} call.
This eliminates all 96 allocations per forward pass, replacing dynamic memory
management with zero-overhead in-place writes.
The buffers are shared across all layers because each \texttt{expand} call
immediately consumes \texttt{out\_A} before the next \texttt{shrink} call
overwrites it.

\subsection{Adapter Store}
\label{sec:adapter_store}

At service startup, \sysname{} pre-loads all tenant LoRA adapters into GPU
memory as an \texttt{AdapterStore}: a dictionary mapping adapter IDs to
\texttt{LoraWeight} objects, each holding tensors
$W_A \in \mathbb{R}^{L \times H \times r}$ and
$W_B \in \mathbb{R}^{L \times r \times H}$
where $L$ is the number of transformer layers.
Matrices are stored in inference-transposed layout ($H \times r$ rather than
$r \times H$ for $A$) so that \texttt{bmm} requires no runtime transpose.

For a batch of adapter IDs, the \texttt227753{BatchAssembler} iterates over the
batch, slices each adapter's per-layer tensor, and \texttt{unsqueeze(0)}-es
it to add a batch dimension.
After all samples are processed, \texttt{torch.cat} concatenates the per-layer
lists into $(\mathcal{B}, H, r)$ tensors ready for \texttt{bmm}.
This CPU-side assembly is the only per-request overhead before the GPU forward
pass (\S\ref{sec:results_latency}).

\subsection{Complexity Analysis}
\label{sec:complexity}

\paragraph{Memory.}
The base model requires $\mathcal{O}(d^2 L)$ memory regardless of tenant
count.
Each adapter requires $\mathcal{O}(r d L)$ memory.
For $N$ tenants: total GPU memory $= \mathcal{O}(d^2 L + N r d L)$.
At $d=1024$, $L=24$, $r=8$: 100 adapters occupy 157~MB; 20{,}000 adapters
occupy 31.5~GB.
An NVIDIA A100-40GB can hold $\approx$25{,}000 adapters at rank 8 before
exhausting memory.

\paragraph{Inference time.}
The latency of a single forward pass is independent of $N$ (adapter count):
it depends only on batch size $\mathcal{B}$, sequence length $S$, and model depth $L$.
The adapter count affects only CPU-side batch assembly time, which is
$\mathcal{O}(\mathcal{B} \cdot L \cdot |\mathcal{M}|)$ where $|\mathcal{M}|$ is the
number of target modules.
Empirically, increasing $N$ from 100 to 20{,}000 at batch size 32 leaves p50
latency effectively unchanged (40.4 vs.\ 40.2~ms;
\S\ref{sec:results_latency}).

\section{Experiments}
\label{sec:experiments}

\subsection{Setup}
\label{sec:setup}

\paragraph{Base model.}
Primary experiments use \texttt{BAAI/bge-m3} \cite{chen2024bge},
a 24-layer XLM-RoBERTa-derived encoder with hidden size $d=1024$,
16 attention heads, and $\approx$568M parameters.
This is among the most widely-served encoders for retrieval and classification
in production multi-tenant systems, and at $d=1024$ with $\approx$568M
parameters it is a demanding setting for the per-request overheads we measure.

\paragraph{LoRA configuration.}
We apply LoRA to the query and value projection matrices of each attention
layer (\texttt{target\_modules = [query, value]}).
We sweep rank $r \in \{4, 8, 16, 32\}$ with $\alpha = r$ (no scaling), matching
the configuration used by our PEFT-equivalence numerical tests.

\paragraph{Hardware.}
Primary experiments run on a single NVIDIA A100-SXM4-40GB GPU on a
cloud-managed node (29 vCPUs, $\approx$230~GB host RAM) with PyTorch 2.11.0+cu128 in
float16 precision.
% TODO: re-add multi-hardware portability cross-ref once §4.5 is restored.

\paragraph{Benchmark protocol.}
We measure end-to-end latency (batch assembly + encoder forward pass + LR head)
using 50 warm-up iterations followed by 200 measured iterations.
GPU-side work is timed with reusable \texttt{torch.cuda.Event} pairs and
synchronized once per iteration; CPU-side assembly is timed with
\texttt{time.perf\_counter} between identical synchronization points.
We sweep adapter count $N \in \{100,\,1{,}000,\,5{,}000,\,10{,}000,\,20{,}000\}$,
batch size $\mathcal{B} \in \{8,\,16,\,32,\,64,\,128\}$, and rank
$r \in \{4,\,8,\,16,\,32\}$.
Each configuration samples mixed-tenant batches uniformly at random from the
adapter pool.

\paragraph{Adapters.}
Latency and throughput experiments use synthetic LoRA weights, which isolates
serving-system overhead from adapter-quality artefacts; we verify in
\S\ref{sec:results_accuracy} that real fine-tuned adapters trained on
classification benchmarks reproduce the same per-batch cost.

\paragraph{Baselines.}
We compare against \texttt{HuggingFace PEFT}~\cite{mangrulkar2022peft} in its
default per-request swap configuration (\S\ref{sec:results_baselines}).
\texttt{vLLM} \cite{kwon2023vllm} supports single-adapter encoder LoRA as of
v0.8.3 but does not yet support multi-adapter classification serving
(in-progress PR~\#24596, unmerged as of submission);
\texttt{LoRAX} \cite{predibase2023lorax} is likewise decoder-oriented.
We therefore omit these from quantitative comparison; see
\S\ref{sec:relwork} for a detailed discussion.

\paragraph{Finding 1: Adapter count does not drive latency.}
Scaling from 100 to 20{,}000 adapters at $\mathcal{B}{=}32$, $r{=}8$ leaves p50 latency
statistically unchanged (40.4 vs.\ 40.2~ms, a 0.5\% difference)---a
200$\times$ increase in the number of served customers at zero latency cost.
The GPU-side forward pass time is constant at $\approx$26.8~ms across the
entire sweep, and the only $N$-dependent component is the CPU-side batch
assembler whose share remains below 35\% of total latency.
This empirically validates the $\mathcal{O}(1)$-in-$N$ scaling property of
\S\ref{sec:complexity}.

\paragraph{Finding 2: Batch size drives throughput up to saturation at $\mathcal{B}{=}64$.}
Throughput scales from 384~samples/sec at $\mathcal{B}{=}8$ to 801~samples/sec at
$\mathcal{B}{=}64$, then plateaus---$\mathcal{B}{=}128$ delivers no further gain (800~samples/sec).
The shared-base encoder forward becomes GPU-bound at $\mathcal{B}{=}64$, after which
larger batches only widen tail latency without lifting throughput.
For deployments under strict p99 SLAs, $\mathcal{B} \in \{32, 64\}$ is the recommended
operating range.

\paragraph{Finding 3: LoRA rank is a free latency knob in the small-rank regime.}
At $N{=}1{,}000$, $\mathcal{B}{=}32$, p50 latency is flat across $r \in \{4, 8, 16, 32\}$
(40.4, 40.1, 40.2, 40.3~ms respectively), with no rank trend in the tail either
(p99 = 44.3, 42.8, 45.6, 40.8~ms). This is the expected behaviour while
$r \ll H$: the low-rank path contributes only $2r/H$ of a base projection's
arithmetic---at most 6\% at $H{=}1024$, $r{=}32$, and $\approx$1\% of the full
encoder forward---so the per-batch GPU forward stays at $\approx$27~ms across all
four ranks. The knob ceases to be free once $2r$ approaches $H$.
Within this regime, practitioners can select rank purely on a quality--memory
basis: doubling rank leaves forward latency unchanged and only doubles the
per-adapter footprint. That footprint is not entirely without consequence---since
\sysname{} holds all adapters GPU-resident, doubling rank halves the per-GPU
tenant ceiling ($\approx$25{,}000 adapters at $r{=}8$ versus $\approx$6{,}000 at
$r{=}32$; Finding~4)---but it does not affect serving latency below that ceiling.

\paragraph{Finding 4: Predictable memory footprint and per-GPU ceiling.}
Per-adapter cache memory measures 1.573~MB at $r{=}8$ in fp16 (24 layers,
hidden size 1024, two target modules), matching the analytic formula
$2 \cdot L \cdot d \cdot r \cdot \text{dtype}$ within 5\%.
On a 40~GB A100, after reserving $\approx$2~GB for base-model parameters and
activation buffers, this yields a clean empirical ceiling of
$\approx$\textbf{25{,}000} adapters at $r{=}8$, $\approx$\textbf{12{,}000} at
$r{=}16$, and $\approx$\textbf{6{,}000} at $r{=}32$.
Our $N{=}50{,}000$ runs OOM'd cleanly at all batch sizes, confirming the limit.

\paragraph{Finding 5: Tail latency widens at large batches.}
The p99/p50 ratio at $\mathcal{B}{=}32$ is $1.04\times$; at $\mathcal{B}{=}64$ it reaches
$2.27\times$ and at $\mathcal{B}{=}128$ remains elevated at $1.69\times$.
Profiling localizes the spike to occasional CPU-side stalls in the
batch-assembly path (\S\ref{sec:results_assembly}); the GPU forward exhibits
no such variance.
Pinning the assembler thread and disabling Python's GC during the measurement
loop is left as a near-term engineering improvement.

\paragraph{Finding 6: Batch assembly is the dominant non-base-model cost.}
\label{sec:results_assembly}
Decomposing each iteration into CPU-side assembly (gather LoRA tensors,
\texttt{stack}, host-to-device copy) versus GPU-side forward, the assembly
share is 16\% at $\mathcal{B}{=}8$ and rises to \textbf{39\%} at $\mathcal{B}{=}128$: the encoder
forward saturates at $\mathcal{B}{=}64$ while assembly continues to scale linearly with
$\mathcal{B}$.
This identifies the per-batch assembler---not the GPU---as the dominant
target for further engineering work; promising directions include
double-buffered host-to-device transfer overlapped with the previous batch's
forward, and a GPU-resident gather that replaces the per-batch host copy with
an \texttt{index\_select} into a GPU-side cache.

\paragraph{Finding 7: Custom LoRA kernels would not move the needle on encoders.}
\label{sec:results_custom_kernels}
A natural question is whether replacing our \texttt{torch.bmm} shrink/expand
operations with custom kernels (Punica's SGMV \cite{chen2024punica} or S-LoRA's
MBGMV \cite{sheng2024slora}) would yield further speedups. The answer is no,
for encoders with hidden size $d=1024$: the LoRA arithmetic is already a
small fraction of the forward cost.
We establish this with three independent measurements at $\mathcal{B}{=}32$, $N{=}1{,}000$,
$r{=}8$ on the same A100-40GB.
First, the \emph{analytic FLOP ratio} per encoder layer is
$12 \mathcal{B} S d^2 / (4 \mathcal{B} S d r) = 3d/r = 384$ -- the base encoder performs
384$\times$ more arithmetic than the LoRA path, so even an instantaneous
LoRA kernel would shave at most 0.26\% of FLOPs.
Second, a PyTorch profiler trace attributes \textbf{1.9\%} of total CUDA time
to \texttt{bmm} operations (the LoRA path), versus 21.6\% for the base linear
layers (Q/K/V/O projections and the FFN).
Third, an end-to-end \emph{zero-LoRA ablation}---running the same kernel
launches but with $A{=}B{=}0$, isolating the wall-clock contribution of the
LoRA arithmetic---measures a forward-time saving of just
\textbf{0.37~ms out of 28.7~ms} (\textbf{1.29\%}) when the LoRA path is
neutralized.
The decoder-LoRA literature reports large speedups from custom kernels because
the per-token decode workload is dominated by small matrix-vector products
where LoRA's relative weight is much higher. For a single-pass encoder forward
at typical $d=1024$, the same engineering investment cannot meaningfully
improve our serving throughput.

\paragraph{PEFT throughput is invariant in batch size.}
Because the sequential path executes one \texttt{set\_adapter} call and one
$\mathcal{B}{=}1$ forward per sample, wall-clock time scales linearly with $\mathcal{B}$ and
throughput remains pinned at $\approx$11.7~samples/sec at $N{=}100$ and
$\approx$1.4~samples/sec at $N{=}1{,}000$.
\sysname{}, in contrast, reaches 800~samples/sec at $\mathcal{B}{=}64$ and saturates
thereafter.

\paragraph{PEFT throughput collapses with adapter count.}
Moving from 100 to 1{,}000 attached adapters degrades PEFT throughput
8.4$\times$ (11.7 $\to$ 1.4~samples/sec)---an $\mathcal{O}(N)$ overhead in the
per-swap path.
\sysname{}'s throughput is statistically identical between $N{=}100$ and
$N{=}20{,}000$ (Table~\ref{tab:main_results}), confirming that the base-encoder
forward path is decoupled from the adapter pool.

\paragraph{Deployment cost.}
Adding 1{,}000 adapters to a PEFT-wrapped model takes 1{,}327~seconds
($\approx$22~minutes) of CPU-bound module construction.
\sysname{}'s \texttt{AdapterStore} accepts 1{,}000 adapters in under
2~seconds---a $\mathbf{>600\times}$ improvement in cold-start time, which is
particularly relevant for elastic deployments and CI evaluation pipelines.

\paragraph{Other systems.}
vLLM \cite{kwon2023vllm} can load single-adapter encoder LoRA weights as of
v0.8.3 (closing GitHub issue \#12808); multi-adapter classification serving is
in-progress (PR \#24596, unmerged as of this submission).
Even when shipped, vLLM's serving runtime is architected around autoregressive
decoding---continuous batching, paged KV-cache, and per-token
scheduling---none of which apply to single-pass encoder classification.
A direct quantitative comparison would therefore conflate LoRA-serving
efficiency with the overhead of vLLM's decoder-oriented scheduler on a
non-native workload; we defer such a comparison to future work and to the
moment PR~\#24596 lands.
LoRAX \cite{predibase2023lorax} is decoder-oriented and does not document
encoder support.

\subsection{Real-Task Accuracy Validation}
\label{sec:results_accuracy}

\paragraph{Correctness.}
We numerically verify that \sysname{}'s output is bit-equivalent to a reference
PEFT-wrapped \texttt{AutoModel} with the same A/B weights to within
\texttt{atol=rtol=1e-4} in fp32 across four scenarios: (i) zero-LoRA against
the raw base encoder, (ii) a single shared adapter applied across the batch,
(iii) distinct per-sample adapters with shared A/B per layer, and (iv)
per-target-module distinct A/B---each implemented as a unit test that runs in
continuous integration on every commit.

\paragraph{Task accuracy.}
To confirm that LoRA adapters served through \sysname{} achieve comparable
classification accuracy to full encoder fine-tuning, we evaluate on seven
public text-classification benchmarks used by the SetFit literature
\cite{tunstall2022efficient}: SST-2, SST-5, CR, Amazon-Counterfactual,
Emotion, EnronSpam, and AG News.
For each dataset we train two variants of \texttt{paraphrase-mpnet-base-v2}
with $N=8$ labeled examples per class: a \emph{vanilla} full-encoder
fine-tune (117M trainable parameters) and a \emph{LoRA} variant at rank~8
(147{,}456 trainable parameters---a $\mathbf{800\times}$ reduction).

\section{Related Work}
\label{sec:relwork}

\paragraph{Multi-tenant LoRA serving for decoder LLMs.}
Punica \cite{chen2024punica} introduces SGMV, a custom CUDA kernel that groups
batch inputs by LoRA model and launches per-group matrix-vector products;
its authors explicitly scope the design to the decode stage, optimizing for
vector-shaped inputs $(1, H)$ over a populated KV cache.
S-LoRA \cite{sheng2024slora} adds a paged memory pool and Triton kernels
(MBGMM/MBGMV) supporting heterogeneous ranks, but its system is built around
the autoregressive prefill$\to$decode pipeline and never exposes the encoder
operations (bidirectional attention, pooling, classification heads) that
classification workloads require.
vLLM \cite{kwon2023vllm} integrates these kernels as its multi-LoRA backend;
it added single-adapter encoder-LoRA loading in v0.8.3, and multi-adapter
classification serving---the scope we target---is in active development
(PR~\#24596, unmerged at submission), which we read as independent
confirmation that the gap is recognized but as yet unaddressed.
LoRAX \cite{predibase2023lorax}, MixLoRA \cite{PLACEHOLDER_mixlora2024},
CaraServe \cite{su2023caraserve}, and dLoRA \cite{wu2024dlora} likewise
optimize decoder-only autoregressive serving and do not address encoder
classifiers, variable-size classification heads, or deployment without custom
CUDA compilation.

\paragraph{Encoder and multi-adapter serving.}
HuggingFace TEI \cite{huggingface2023tei} serves encoder/embedding models at
high throughput via Flash Attention and cuBLASLt but has no adapter support:
all tenants must share identical weights.
PetS \cite{zhou2022pets} is the closest prior system, targeting multi-adapter
encoder serving for Adapter \cite{PLACEHOLDER_houlsby2019}, BitFit
\cite{PLACEHOLDER_bitfit2022}, and MaskBERT \cite{PLACEHOLDER_maskbert2020} on
BERT/DistilBERT; it predates LoRA, does not support low-rank decompositions,
and does not handle per-tenant classification heads.
Jina-embeddings-v3 \cite{gunther2024jina} bakes five task-specific LoRA
adapters into a single encoder for mixed-adapter batching, but as a fixed
\emph{model design} it cannot admit new tenants without retraining.
\sysname{} is a LoRA-native serving framework that batches arbitrary external
adapters---with variable classification heads and a pre-loaded cache---without
modifying the base model.

\section{Conclusion}
\label{sec:conclusion}

We presented \sysname, a system for multi-tenant LoRA serving on encoder
models that fills a gap left by all existing systems: none support
heterogeneous batching of different LoRA adapters in a single encoder forward
pass.
\sysname{} achieves this through late-fusion batched matrix multiplication---a
decomposition that separates the frozen base-model path from the per-tenant
LoRA delta path and fuses them additively, enabling mixed-tenant batches
without weight merging, custom CUDA kernels, or KV-cache machinery.
On an NVIDIA L4 GPU with \texttt{multilingual-e5-small}, \sysname{} serves
5{,}000 pre-loaded adapters at 556~samples/sec in 56~ms p50 latency,
with sub-linear growth in latency as adapter count increases 50-fold.
\sysname{} requires only standard PyTorch, making it immediately deployable
on managed cloud GPU environments where custom kernel compilation is
unavailable---the majority of production NLP serving infrastructure today.

\section*{Limitations}

\paragraph{Uniform rank constraint.}
All adapters in a batch must share the same rank $r$ and the same set of
target modules.
Serving tenants with heterogeneous fine-tuning strategies requires padding
every adapter to the maximum rank present in the batch, wasting compute on
low-rank adapters; a masked-BMM variant that avoids this padding overhead
remains future work.
% TODO (Task #8): mixed-rank experiment, finalize this paragraph after.

\paragraph{Pre-loaded adapter cache.}
\sysname{} holds all adapters in GPU memory permanently.
For workloads with more than $\sim$16{,}000 adapters at rank 8 on an L4, an
LRU eviction policy with CPU offload would be required.
Paged adapter storage analogous to PagedAttention
\cite{kwon2023vllm} is a natural extension.

\paragraph{CPU-side batch assembly.}
The \texttt{BatchAssembler} runs on CPU and involves Python loops with
\texttt{torch.cat}.
For very high request rates ($>$10{,}000 requests/sec), this becomes the
throughput bottleneck.
A custom CUDA or C++ gather kernel that indexes directly into the adapter
store would eliminate this overhead, at the cost of departing from
pure-PyTorch deployability.

\paragraph{Single-seed evaluation.}
Current benchmarks use a single random seed, so statistical significance is
not yet established.
% TODO (Task #6): multi-seed CI runs before camera-ready.

\paragraph{Synthetic-only adapter validation.}
Latency and throughput numbers are obtained with randomly initialized adapters
($B = 0$, so the LoRA delta is zero).
Real adapters with non-zero deltas will have marginally higher GPU compute
time; end-to-end correctness against PEFT-merged references is verified
numerically (\S\ref{sec:results_accuracy}) but not yet across the full
serving pipeline.

\section*{Ethics Statement}

This work addresses inference-time efficiency for multi-tenant NLP systems.
We identify no specific ethical concerns beyond those inherent to the
underlying models (\eg bias in pre-trained encoders).
The system is intended for legitimate multi-tenant SaaS deployments.
Adapter isolation is enforced by design: per-tenant weights are never merged
into the shared base model, eliminating cross-tenant contamination risks
present in weight-merging approaches.
