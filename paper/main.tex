\begin{abstract}
  Low-Rank Adaptation (LoRA) has become a popular method to adapt
  pre-trained models to specific domains. Applied to encoders in a
  multi-tenant service, it lets each tenant specialize a shared model
  for classification, retrieval, or ranking. Existing
  multi-tenant LoRA serving systems target autoregressive decoders,
  and for encoders the available tooling supports only per-request
  adapter swapping, whose cost grows with the number of registered
  adapters. We observe that, unlike decoder generation, the encoder
  forward pass is compute-bound and dominated by the shared base
  projections, so per-tenant adaptation can be expressed as plain
  batched matrix multiplication with no custom kernels. We present
  \sysname, a pure-PyTorch system that serves many different
  LoRA-adapted encoders in a single shared forward pass on one GPU.
  \sysname{} fuses adapters late, in activation space: the base
  projections run once over the mixed-tenant batch, while per-sample
  low-rank deltas and per-tenant classification heads are applied as
  batched matrix multiplications.
  Tenant weights are never merged into the shared base, ruling out
  cross-tenant contamination by construction. Our evaluation shows
  that \sysname's serving latency stays flat as the adapter pool
  grows to tens of thousands on a single GPU, and that it achieves
  \SpeedupMixedMin--\SpeedupMixedMax$\times$ higher throughput than
  HuggingFace PEFT's native mixed-batch API and up to
  \HeadlineSpeedupHigh$\times$ over per-adapter swapping, while
  registering new adapters over \ColdStartSpeedupMin{}$\times$ faster.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Enterprise NLP features, such as intent detection \cite{arora2024intent}, ticket routing,
and text classification, require low latency and predictable cost at
high request volume.
In multi-tenant environments, these workloads are typically served by a
shared bidirectional encoder with tenant-specific task heads.
Fine-tuning the encoder parameters alongside the task head
yields consistent accuracy gains over a frozen shared encoder
\cite{devlin2019bert,tunstall2022efficient,jain2026succeeding}.
Serving an isolated, fully fine-tuned model per tenant, however, is
infeasible at scale.
At $\approx$\BgeFpSixteenGB{}~GB per copy in float16 precision, serving
20{,}000 tenants would require \StorageTwentyKTB{}~TB of model
weights (requiring \StorageTwentyKGPUs{} A100-80GB GPUs) and eliminate any
opportunity for cross-tenant request batching.
Low-Rank Adaptation (LoRA) \cite{hu2022lora} removes the storage barrier
by expressing tenant-specific adaptations as low-rank updates to the
shared base encoder: it retains \SetfitBgeRetainsPct{}\% of full
fine-tuning's mean accuracy while shrinking the per-tenant footprint
to just \LoraBytesREightMB{}~MB (rank~\HeadlineRank{}, \BgeLayers{}
layers)—a \StorageReductionFullVsLoraRankEight$\times$ reduction.
The remaining challenge is \textbf{batched serving} across these
heterogeneous adapters on a shared GPU.

Existing multi-tenant LoRA serving systems like Punica
\cite{chen2024punica}, S-LoRA \cite{sheng2024slora}, vLLM
\cite{kwon2023vllm}, and LoRAX \cite{predibase2023lorax} are tailored
for autoregressive decoder workloads, where custom CUDA kernels and
paged-memory pools optimize memory-bound, token-by-token generation
over a KV cache.
Meanwhile, on the encoder side, runtimes do not support mixed-tenant
LoRA serving: vLLM lacks a runtime LoRA path for encoder models, TEI
serves encoders without adapters, and PEFT's mixed-batch API is
restricted to sequential adapter sub-batching and cannot route
per-tenant heads (\S\ref{sec:relwork}).

Encoder workloads exhibit fundamentally different dynamics from
decoder generation: the bidirectional forward pass at sequence length $S \gg 1$
is compute-bound and dominated by the base model's projection weights.
Consequently, the LoRA compute path accounts for only
\ProfLoraBmmIsolatedPct{}\% of the total forward GPU time, meaning
custom CUDA kernels yield minimal, single-digit performance gains
(\S\ref{sec:results_custom_kernels}, Finding~6).
This structural difference makes standard batched matrix
multiplication (BMM) the appropriate primitive for encoder serving.

We present \sysname, a serving system built on this primitive.
Its design hinges on \emph{where} the adapter is applied: merging
$B_i A_i$ into $W_0$ yields a per-sample weight matrix $W'_i$ that must be
applied serially, whereas keeping the base output $W_0 x$ and the delta
$B_i A_i x$ as separate terms and summing them lets the per-sample work
run as batched matrix multiplication. We call this
\emph{activation-space} fusion, as opposed to parameter-space
merging. \sysname{} runs the shared base path once over
a mixed-tenant batch of size $\mathcal{B}$ and dispatches the per-sample LoRA paths in
parallel via \texttt{torch.bmm}, so the batch completes in a single forward pass regardless of how
many distinct adapters it references. Per-tenant task heads
(variable-size classifiers, regressors, retrieval re-rankers) are
batched analogously via zero-padded BMM.

Our single-GPU evaluation characterizes this serving primitive; a
minimal reference deployment for stateless scale-out is in
Appendix~\ref{sec:deployment}.

\paragraph{Contributions.}
\begin{itemize}
  \item We identify and characterize the \emph{encoder multi-tenant LoRA
    serving} problem, and show that existing systems leave it unsolved
    (\S\ref{sec:relwork}).

  \item We present late-fusion BMM serving, an architecture that batches
    arbitrary mixed-tenant encoder requests without weight merging and
    without custom CUDA kernels, in standard PyTorch, removing the
    custom-kernel build step, a common source of deployment friction
    on managed GPU platforms (\S\ref{sec:system},
    Appendix~\ref{sec:deployment}).

  \item We validate the served workload: under the SetFit few-shot
    protocol on seven classification benchmarks, rank-\HeadlineRank{}
    LoRA retains \SetfitRetainsPct\% and \SetfitBgeRetainsPct\% of full
    fine-tuning's mean accuracy on \texttt{paraphrase-mpnet-base-v2}
    (Table~\ref{tab:accuracy}, \S\ref{sec:background_lora}) and the
    \texttt{BAAI/bge-m3} serving model (Table~\ref{tab:accuracy_bge},
    Appendix~\ref{app:accuracy}), where it also improves over a shared
    frozen encoder, justifying per-tenant adaptation over a single
    shared model.

  \item We empirically demonstrate that adapter count does not drive
    inference latency: scaling from 100 to \HeadlineCapacity{} adapters at batch
    size \HeadlineBatch{} on a single A100 leaves p50 latency flat
    (\PFiftyAtNHundred$\to$\PFiftyAtNFortySevenK~ms) and p99 bounded
    (\S\ref{sec:experiments}).

  \item We benchmark \sysname{} against HuggingFace PEFT on identical
    hardware:
    \textbf{\SpeedupMixedMin--\SpeedupMixedMax$\times$} higher throughput
    than PEFT's native mixed-batch API and up to
    \textbf{\HeadlineSpeedupHigh$\times$} over per-adapter swapping,
    \textbf{$>$\ColdStartSpeedupMin{}$\times$} faster cold-start
    deployment, and \texttt{set\_adapter} isolated as the
    $\mathcal{O}(N)$ bottleneck in the standard PEFT baseline
    (\S\ref{sec:results_baselines}, Finding~7).
\end{itemize}

\section{Background}
\label{sec:background}

\subsection{LoRA for Encoder Models}
\label{sec:background_lora}

LoRA \cite{hu2022lora} decomposes a weight update $\Delta W \in
\mathbb{R}^{d \times d}$ as the product of two low-rank matrices:
\begin{equation}
  \Delta W = B A, \quad
  A \in \mathbb{R}^{r \times d},\;
  B \in \mathbb{R}^{d \times r},\;
  r \ll d.
\end{equation}
The full forward pass for a single sample becomes
$h = W_0 x + \frac{\alpha}{r} B A x$,
where $W_0$ is the frozen pre-trained weight and $\alpha$ is a scaling
hyperparameter typically set equal to $r$.
For an encoder of hidden size $d = \BgeHidden$ with $L = \BgeLayers$
layers, applying LoRA
at rank $r = \HeadlineRank$ to the query and value projections yields
$2 L \cdot (d r + r d) = \LoraParamsREight$ trainable parameters per adapter, representing a
$\LoraReductionVsQVRankEight\times$ reduction over full fine-tuning
of those layers.

In this work, $B$ is initialized to zero so that $\Delta W = 0$ at the start
of training, leaving the pre-trained representations intact.

Our evaluation shows that at rank \HeadlineRank, LoRA retains \SetfitRetainsPct\% of vanilla
fine-tuning's mean
accuracy across seven public text-classification benchmarks
(Table~\ref{tab:accuracy}; per-task drop \SetfitMinDropPP--\SetfitMaxDropPP pp),
at $1/\MpnetParamReductionRankEight$ the trainable-parameter
cost.\footnote{Accuracy reported on
  \texttt{paraphrase-mpnet-base-v2} to match the SetFit literature
  \cite{tunstall2022efficient}; on \texttt{BAAI/bge-m3}, the serving
  encoder, LoRA shows the same pattern and beats a frozen-encoder
  baseline on all seven tasks
(Table~\ref{tab:accuracy_bge}, Appendix~\ref{app:accuracy}).} The remaining
barrier is \emph{serving}: combining thousands of
these adapters in a single forward pass.

\subsection{The Multi-Tenant Serving Problem}
\label{sec:background_serving}

Consider a classification service for $N$ customers, each with a custom
\texttt{BAAI/bge-m3} \cite{chen2024bge} adapter. Three naive serving strategies
fail at scale:
(1)~\emph{One model per tenant} requires a full base model copy per customer
and lacks cross-tenant batching;
(2)~\emph{Dynamic weight merging} ($W' = W_0 + B_i A_i$ in-place) serializes requests,
fragments memory, and introduces concurrency risks;
(3)~\emph{Sequential batching} processes tenants one-by-one, driving average GPU
utilization toward $1/N$.
An effective solution must batch \emph{heterogeneous} adapters (distinct weights,
identical shapes) in a single forward pass, applying sample-specific linear
operations concurrently without serialization.

\section{Related Work}
\label{sec:relwork}

\paragraph{Multi-tenant LoRA serving for decoder LLMs.}
Punica \cite{chen2024punica} (SGMV, a custom CUDA kernel grouping a batch by
LoRA id for per-group matrix-vector products) and S-LoRA \cite{sheng2024slora}
(a paged memory pool with Triton MBGMM/MBGMV kernels for heterogeneous ranks)
both scope their designs to the autoregressive prefill$\to$decode pipeline and
never expose the encoder operations (bidirectional attention, pooling, and
classification heads) that classification workloads require. vLLM
\cite{kwon2023vllm} adopts these kernels as its multi-LoRA backend, but its
encoder model classes do not implement them---v0.23.0 rejects
\texttt{enable\_lora} for \texttt{BAAI/bge-m3} at
initialization---and multi-adapter
classification serving remains an unmerged draft (PR~\#24596). LoRAX
\cite{predibase2023lorax}, CaraServe \cite{li2024caraserve}, and dLoRA
\cite{wu2024dlora} likewise optimize decoder-only serving and do not address
encoder classifiers, variable-size classification heads, or deployment without
custom CUDA compilation.

\paragraph{Encoder and multi-adapter serving.}
HuggingFace TEI \cite{huggingface2023tei} serves encoder/embedding models at
high throughput via Flash Attention and cuBLASLt but has no adapter support
(an open feature request as of
June~2026).\footnote{\url{https://github.com/huggingface/text-embeddings-inference/issues/788}}
In production multi-tenant retrieval, Vishwanathan et
al.~\cite{vishwanathan2022multitenant} serve a shared sentence
bi-encoder with per-tenant fine-tuned final-layer weights, switching
tenant-specific weights per request, which forces each request to be
single-tenant, a limitation that \sysname{} removes.
PetS \cite{zhou2022pets}, the closest prior system, targets multi-adapter
encoder serving for Adapter \cite{houlsby2019adapter}, BitFit
\cite{benzaken2022bitfit}, and MaskBERT \cite{zhao2020masking} on
BERT/DistilBERT, but predates LoRA and handles neither low-rank decompositions
nor per-tenant classification heads.
\sysname{} is a LoRA-native framework that batches arbitrary external
adapters (with variable classification heads and a pre-loaded cache) without
modifying the base model.

\subsection{Late-Fusion Decomposition}
\label{sec:lf_decomp}

The core insight is that the LoRA forward pass
$h = W_0 x + B_i A_i x$
can be split into two \emph{independent} computations:
\begin{align}
  h_{\text{base}} &= W_0 x \label{eq:base} \\
  h_{\text{delta}} &= B_i (A_i x) \label{eq:delta} \\
  h &= h_{\text{base}} + h_{\text{delta}} \label{eq:fuse}
\end{align}

Equation~\ref{eq:base} uses the same frozen $W_0$ for every sample in the
batch and is computed by standard PyTorch linear layers.
Equation~\ref{eq:delta} applies a \emph{different} $(A_i, B_i)$ pair to each
sample $i$, which requires batched matrix multiplication rather than a
broadcast multiply.
Equation~\ref{eq:fuse} is a zero-allocation element-wise addition.

For a batch of $\mathcal{B}$ samples with hidden size $H$ and
sequence length $S$:
\begin{align}
  h_{\text{shrink}} &= \texttt{bmm}(x,\; [A_0,\ldots,A_{\mathcal{B}-1}])
  \in \mathbb{R}^{\mathcal{B} \times S \times r} \label{eq:shrink} \\
  h_{\text{delta}} &= \texttt{bmm}(h_{\text{shrink}},\;
  [B_0,\ldots,B_{\mathcal{B}-1}])
  \in \mathbb{R}^{\mathcal{B} \times S \times H} \label{eq:expand}
\end{align}

\noindent
where $[A_0, \ldots, A_{\mathcal{B}-1}] \in \mathbb{R}^{\mathcal{B}
\times H \times r}$ is the
stack of per-sample shrink matrices, assembled from the adapter store at
request time.
Each \texttt{bmm} call is a single GPU kernel launch, processing
all $\mathcal{B}$
samples simultaneously regardless of how many distinct adapters they reference.

Unlike the custom kernels of Punica \cite{chen2024punica} and
S-LoRA \cite{sheng2024slora}, which group or gather inputs by
adapter id and target the autoregressive prefill$\to$decode
pipeline, \texttt{torch.bmm} applies a distinct $(A_i, B_i)$ to
every batch item on the dense $(S, H)$ encoder forward pass
(\S\ref{sec:relwork}).

\subsection{Batched Classification Heads}
\label{sec:lr_head}

In the multi-tenant classification setting, each tenant trains a
logistic-regression (LR) head on top of the encoder's pooled
\texttt{[CLS]} representation.
Tenants differ in the number of output classes: tenant $i$ may have $c_i$
classes where $c_i$ varies from 2 to over 100.

\sysname{} serves all heads in a single BMM call.
Given a batch of pooled representations
$p \in \mathbb{R}^{\mathcal{B} \times 1 \times H}$
and per-tenant weight matrices
$W^{\text{cls}}_i \in \mathbb{R}^{c_i \times H}$ and bias vectors
$b^{\text{cls}}_i \in \mathbb{R}^{c_i}$,
we zero-pad all weight matrices to the maximum label count
$c_{\max} = \max_i c_i$ in the batch and form a stacked tensor
$W^{\text{cls}} \in \mathbb{R}^{\mathcal{B} \times c_{\max} \times H}$.
The logit computation is:
\begin{equation}
  \text{logits} = \texttt{bmm}(p,\; {W^{\text{cls}}}^\top) + b^{\text{cls}}
  \;\in\; \mathbb{R}^{\mathcal{B} \times 1 \times c_{\max}}
\end{equation}

Callers slice $[:, :, :c_i]$ per sample before applying softmax.
Because these padded dimensions are discarded prior to softmax, they
have no effect on the resulting probability distribution of any tenant.

\subsection{Implementation}
\label{sec:impl}

\paragraph{Pre-allocated buffers.}
A naive implementation lets \texttt{torch.bmm} allocate a fresh output
tensor on every call, producing $2 \times |\mathcal{M}| \times L$
allocations per forward pass, adding several hundred microseconds of
pure CUDA-allocator overhead per batch.
\sysname{} instead pre-allocates two fixed-size buffers at initialization,
$\mathtt{out\_A} \in \mathbb{R}^{\mathcal{B}_{\max} \times S_{\max} \times r}$
and $\mathtt{out\_B} \in \mathbb{R}^{\mathcal{B}_{\max} \times
S_{\max} \times H}$,
and passes them via the \texttt{out=} argument of every \texttt{bmm} call.
Both are shared across layers because each \texttt{expand} consumes
\texttt{out\_A} before the next \texttt{shrink} overwrites it.

\paragraph{Adapter store and batch assembly.}
At service startup, \sysname{} pre-loads all tenant LoRA adapters into GPU
memory as an \texttt{AdapterStore}: a dictionary mapping adapter IDs to
\texttt{LoraWeight} objects holding
$W_A \in \mathbb{R}^{L \times H \times r}$ and
$W_B \in \mathbb{R}^{L \times r \times H}$, stored in inference-transposed
layout so \texttt{bmm} requires no runtime transpose.
For a batch of adapter IDs, the \texttt{BatchAssembler} gathers each
adapter's per-layer $W_A$/$W_B$ slices into per-layer Python lists. This
CPU-side gather---a loop over samples, layers, and target modules---is the
dominant per-request overhead before the GPU forward pass
(\S\ref{sec:results_latency}). The per-layer lists are concatenated into
$(\mathcal{B}, H, r)$ and $(\mathcal{B}, r, H)$ tensors lazily inside the
forward, one \texttt{torch.cat} per layer immediately before its
\texttt{bmm}, so this concatenation is attributed to forward rather than
assembly time.

\subsection{Complexity Analysis}
\label{sec:complexity}

\paragraph{Memory.}
The base model requires $\mathcal{O}(d^2 L)$ memory regardless of tenant
count.
Each adapter requires $\mathcal{O}(r d L)$ memory.
For $N$ tenants: total GPU memory $= \mathcal{O}(d^2 L + N r d L)$.
At $d=\BgeHidden$, $L=\BgeLayers$, $r=\HeadlineRank$: 100 adapters occupy
\CacheNHundredMB~MB; 20{,}000 adapters occupy \CacheNTwentyKGB~GB.
An A100-80GB can hold \CapacityRankEight{} adapters at rank \HeadlineRank{}
before exhausting memory.

\paragraph{Inference time.}
The latency of a single forward pass is independent of $N$ (adapter count):
it depends only on batch size $\mathcal{B}$, sequence length $S$, and
model depth $L$.
The adapter count affects only CPU-side batch assembly time, which is
$\mathcal{O}(\mathcal{B} \cdot L \cdot |\mathcal{M}|)$ where
$|\mathcal{M}|$ is the
number of target modules.
We validate both properties empirically in \S\ref{sec:results_latency}
(Findings~1 and~5).

\section{Experiments}
\label{sec:experiments}

\subsection{Setup}
\label{sec:setup}

\paragraph{Base model.}
Primary experiments use \texttt{BAAI/bge-m3} \cite{chen2024bge},
a \BgeLayers-layer XLM-RoBERTa-derived encoder with hidden size $d=\BgeHidden$,
\BgeHeads{} attention heads, and \BgeParamsM{}M parameters.
This is among the most widely-served encoders for retrieval and classification
in production multi-tenant systems, and at $d=\BgeHidden$ with \BgeParamsM{}M
parameters it is a demanding setting for the per-request overheads we measure.

\paragraph{LoRA configuration.}
We apply LoRA to the query and value projection matrices of each attention
layer (\texttt{target\_modules = [query, value]}).
We sweep rank $r \in \{4, 8, 16, 32\}$ with $\alpha = r$ (no scaling), matching
the configuration used by our PEFT-equivalence numerical tests.

\paragraph{Hardware.}
Primary experiments run on a single \HeadlineGPU{} GPU on a
cloud-managed node with PyTorch \EnvTorchVersion{} in
\HeadlineDtype{} precision.
We measure end-to-end on one node.

\paragraph{Benchmark protocol.}
We measure end-to-end latency (batch assembly + encoder forward pass + LR head)
using \SysWarmup{} warm-up iterations followed by \SysIters{} measured
iterations for \sysname{}; the PEFT baselines use \PeftWarmup{}/\PeftIters{}
because PEFT-grouped reaches $\sim$80~s/iter at the largest
configuration and 200 iterations would dominate wall-clock without
sharpening an order-of-magnitude speedup claim.
GPU-side work is timed with reusable \texttt{torch.cuda.Event} pairs and
synchronized once per iteration; CPU-side assembly is timed with
\texttt{time.perf\_counter} between identical synchronization points.
We sweep adapter count $N \in \{100$, $1{,}000$, $5{,}000$, $10{,}000$,
$20{,}000$, $40{,}000$, $\CapacityRankEight\}$,
batch size $\mathcal{B} \in \{8,\,16,\,32,\,64,\,128\}$, and rank
$r \in \{4,\,8,\,16,\,32\}$.
Each configuration samples mixed-tenant batches uniformly at random from the
adapter pool.

\paragraph{Adapters and correctness.}
Benchmarks use synthetic LoRA weights to isolate system overhead. We enforce
numerical equivalence to reference HuggingFace and PEFT models to within
$\text{atol}=\text{rtol}=10^{-4}$ in fp32. This is verified via unit tests
across five routing and padding scenarios under both BERT and XLM-RoBERTa
position-id conventions.

\paragraph{Baselines.}
We compare against \texttt{HuggingFace PEFT}~\cite{mangrulkar2022peft} in
four configurations described in \S\ref{sec:results_baselines}, including
its native mixed-batch API (\texttt{adapter\_names}), which does not route
per-request classification
heads,\footnote{\url{https://github.com/huggingface/peft/issues/1960}}
a requirement of our workload.
\texttt{vLLM} \cite{kwon2023vllm} has no runtime LoRA path for encoder
models and \texttt{LoRAX} \cite{predibase2023lorax} is decoder-oriented;
we omit both from quantitative comparison (\S\ref{sec:relwork}).
All PEFT configurations time the bare encoder forward with no
classification head, whereas \sysname{} latencies include batch
assembly and the per-tenant head; the comparison is therefore
conservative in PEFT's favor.

\paragraph{Finding 1: Adapter count does not drive latency.}
Scaling from 100 to \CapacityRankEight{} adapters at
$\mathcal{B}{=}\HeadlineBatch$, $r{=}\HeadlineRank$ shifts p50 latency
by only \PFiftyDriftPctNHundredToFortySevenK\%---within one
between-seed s.d.\ (Table~\ref{tab:main_results})---a
\CustomerMultiplierHundredToFortySevenK$\times$ increase in
served customers at negligible latency cost, sustained to the per-GPU
memory ceiling
(Finding~4).
The GPU-side forward pass time is constant at
\ForwardMsConstantBThirtyTwo~ms across the
entire sweep, and the only $N$-dependent component is the CPU-side batch
assembler, whose share stays at or below
\AssemblePctCeilingBThirtyTwo\% of total
latency---empirically validating the $\mathcal{O}(1)$-in-$N$ scaling of
\S\ref{sec:complexity}.

\paragraph{Finding 2: Batch size drives throughput up to saturation
at $\mathcal{B}{=}64$.}
Throughput scales from \QpsAtBEight~samples/sec at $\mathcal{B}{=}8$
to \QpsAtBSixtyFour~samples/sec at
$\mathcal{B}{=}64$, then plateaus---$\mathcal{B}{=}128$ delivers no
further gain (\QpsAtBOneTwentyEight~samples/sec).
The shared-base encoder forward becomes GPU-bound at $\mathcal{B}{=}64$;
beyond $\mathcal{B}{=}32$, larger batches mainly widen tail latency
(Finding~5), making $\mathcal{B}{=}32$ the operating
point under strict p99 SLAs and $\mathcal{B}{=}64$ the
throughput-optimal choice when tails are tolerable.

\paragraph{Finding 3: LoRA rank is a free latency knob in the
small-rank regime.}
At $N{=}1{,}000$, $\mathcal{B}{=}\HeadlineBatch$, p50 latency is flat
across $r \in \{4, 8, 16, 32\}$, and tail latency shows no resolvable
rank trend (the \PNinetyNineRankSpreadPct\% p99 spread is comparable to
the between-seed s.d.; Table~\ref{tab:main_results}). While $r \ll H$, the
low-rank path adds only
$2r/H$ of a base projection's arithmetic ($\approx$1\% of the full encoder
forward), so the per-batch GPU forward stays at
$\approx$\FwdMsAtREight~ms across all four
ranks; the knob ceases to be free once $2r$ approaches $H$.
Within this regime, rank is a pure quality--memory tradeoff: doubling it leaves
forward latency unchanged but doubles the per-adapter footprint, halving the
per-GPU tenant ceiling (\CapacityRankEight{} adapters at
  $r{=}\HeadlineRank$ versus
\CapacityRankThirtyTwo{} at $r{=}32$; Finding~4).

\paragraph{Finding 4: Predictable memory footprint and per-GPU ceiling.}
Per-adapter cache memory measures \LoraBytesREightMB~MB at
$r{=}\HeadlineRank$ in fp16, matching the
analytic formula $2 \cdot M \cdot L \cdot d \cdot r \cdot \text{dtype}$ exactly.
On an 80~GB A100, after reserving \BaseActivationOverheadGB~GB for base-model
parameters and activation buffers, this yields a clean empirical ceiling of
\textbf{\CapacityRankEight{}} adapters at $r{=}\HeadlineRank$ (the
  largest pool we verified,
occupying \GpuGBAtNFortySevenK~GB), \textbf{\CapacityRankSixteen{}} at
$r{=}16$, and \textbf{\CapacityRankThirtyTwo{}} at $r{=}32$.
Our $N{=}50{,}000$ runs OOM'd cleanly at all batch sizes, confirming the limit.

\paragraph{Finding 5: Batch assembly is the residual bottleneck and
drives tail latency.}
\label{sec:results_assembly}
The CPU-side batch-assembly path (gather per-sample LoRA slices into
per-layer lists, pad the LR head, host-to-device copy) consumes
\AssemblePctAtBEight\% of iteration time at $\mathcal{B}{=}8$ and
\textbf{\AssemblePctAtBOneTwentyEight\%} at $\mathcal{B}{=}128$, scaling
linearly with $\mathcal{B}$ while the encoder forward saturates at
$\mathcal{B}{=}64$.
This same path drives tail latency: the p99/p50 ratio is
$\PNinetyNineOverPFiftyAtBThirtyTwo\times$ at
$\mathcal{B}{=}\HeadlineBatch$ but reaches
$\PNinetyNineOverPFiftyAtBSixtyFour\times$ at $\mathcal{B}{=}64$, with
profiling localizing the spike to occasional Python/GC stalls during
assembly; the GPU forward exhibits no such variance.
Double-buffered H2D transfer and a GPU-resident \texttt{index\_select} gather
would amortize this; both are future work.

\paragraph{Finding 6: Custom LoRA kernels offer only single-digit upside on
encoders.}
\label{sec:results_custom_kernels}
Could custom kernels (Punica's SGMV \cite{chen2024punica}, S-LoRA's MBGMV
\cite{sheng2024slora}) replacing our \texttt{torch.bmm} help? Three measurements
at $\mathcal{B}{=}\HeadlineBatch$, $N{=}1{,}000$, $r{=}\HeadlineRank$ bound the
upside to single digits. The \emph{analytic FLOP ratio} per layer is
$3d/r{=}\FlopBaseToLoraRatio$, so even an instantaneous LoRA kernel
saves at most
\FlopMaxLoraSavingsPct\% of FLOPs. A \emph{profiler trace} (self CUDA time,
isolating the LoRA shrink/expand via an apply-LoRA on/off difference) attributes
\textbf{\ProfLoraBmmIsolatedPct\%} of forward GPU time to the LoRA \texttt{bmm}
versus \textbf{\ProfBaseLinearPct\%} for the base projections. A
\emph{no-LoRA ablation} skipping the entire LoRA path (gather, shrink/expand,
merge) saves \textbf{\AblationLoraCostMs~ms of \AblationLoraOnMs~ms}
(\textbf{\AblationLoraCostPct\%}); the gather and merge,
not the \texttt{bmm}, dominate the gap above the
\ProfLoraBmmIsolatedPct\% kernel cost. Custom fused
kernels target only this path, so \AblationLoraCostPct\% is the hard
ceiling here.

\subsection{Comparison with Baselines}
\label{sec:results_baselines}

We compare against \texttt{HuggingFace PEFT} \cite{mangrulkar2022peft} in four
configurations, all attaching $N$ adapters via \texttt{add\_adapter}.
\emph{Grouped} buckets a mixed batch by adapter id, running one
\texttt{set\_adapter} and forward per bucket (Punica's SGMV strategy
\cite{chen2024punica}). \emph{Mixed} is PEFT's native mixed-batch API
(\texttt{adapter\_names}): one shared base forward with a per-layer loop over
the adapters present in the batch (\S\ref{sec:setup}).
\emph{Homogeneous}, PEFT's friendliest case, uses
single-tenant batches---one \texttt{set\_adapter} and one batched forward each.
\emph{Base} is the bare model with no adapters
(\PeftBaseQpsAtBEight/\PeftBaseQpsAtBThirtyTwo/\PeftBaseQpsAtBOneTwentyEight{}~samples/sec
at $\mathcal{B}{=}8/32/128$, $N$-independent).
We also report PEFT's $N$-adapter registration cost: \texttt{add\_adapter}
re-validates the growing adapter set on each call, so loading the pool takes
\PeftGroupedAddAdapterSecNHundred~s at $N{=}100$ and
\PeftGroupedAddAdapterSecNOneK~s at $N{=}1{,}000$, versus
\LateFuseColdLoadSecNHundred~s and \LateFuseColdLoadSecNOneK~s for \sysname{}'s
constant-time \texttt{AdapterStore} preload---a
\ColdStartSpeedupMin--\ColdStartSpeedupNOneK$\times$ reduction.

\paragraph{Finding 7: PEFT's per-swap cost is $\mathcal{O}(N)$ in the
tenant pool.}
\emph{Homogeneous} batching---PEFT's best case (single-tenant batches, one
\texttt{set\_adapter} and forward each)---is competitive at $N{=}100$, even

holding batching fixed and growing the pool to 1{,}000 collapses throughput

grows $100\to1{,}000$), leaving \sysname{}
\SpeedupMixedMin--\SpeedupMixedMax$\times$ faster across the measured grid.

\section{Conclusion}
\label{sec:conclusion}

We presented \sysname, a serving system for multi-tenant LoRA on encoder
models built on late-fusion batched matrix multiplication. The broader
lesson is that encoder serving inverts the economics that justify custom
LoRA kernels on decoders: at sequence length $S \gg 1$ the adapter path
is just \ProfLoraBmmIsolatedPct\% of forward GPU time, so the custom
kernels that dominate decoder systems (Punica, S-LoRA) are bounded to
single-digit percentage gains here, while standard \texttt{torch.bmm} needs no
compilation step and deploys on managed GPU platforms as-is. The residual
cost has moved off the GPU---CPU-side batch assembly, not the forward
pass, now bounds tail latency---so host-side gather and transfer, not
faster kernels, is where further work belongs. For teams serving a
personalized encoder feature across thousands of tenants, the upshot is
that a single commodity GPU and a stock PyTorch stack replace a fleet of
per-tenant deployments.

\section*{Limitations}

\paragraph{Uniform rank constraint.}
All adapters in a batch must share the same rank $r$ and the same set of
target modules.
Serving tenants with heterogeneous fine-tuning strategies requires padding
every adapter to the maximum rank present in the batch, wasting compute on
low-rank adapters; a masked-BMM variant that avoids this padding overhead
remains future work.
% TODO (Task #8): mixed-rank experiment, finalize this paragraph after.

\paragraph{Pre-loaded adapter cache.}
\sysname{} holds all adapters in GPU memory permanently.
Workloads whose adapter population exceeds a single GPU's capacity require
an LRU eviction policy with CPU offload, or paged adapter storage analogous
to PagedAttention \cite{kwon2023vllm}; both are natural extensions.

\paragraph{CPU-side batch assembly.}
The \texttt{BatchAssembler} runs on CPU and gathers per-sample adapter
slices into per-layer lists via Python loops.
For very high request rates ($>$10{,}000 requests/sec), this becomes the
throughput bottleneck.
A custom CUDA or C++ gather kernel that indexes directly into the adapter
store would eliminate this overhead, at the cost of departing from
pure-PyTorch deployability. Alternatively, moving the adapter cache into a
single contiguous GPU tensor and performing batch assembly via GPU-resident
index selection (e.g., \texttt{torch.index\_select}) represents a promising path to
eliminate this CPU bottleneck while retaining pure-PyTorch compatibility, which
can be optimized further via \texttt{torch.compile}.

\paragraph{Single-node evaluation.}
All latency and throughput results are measured on one GPU. The architecture
targets horizontal scale-out via stateless, tenant-sticky replicas, with a
reference Kubernetes deployment provided (Appendix~\ref{sec:deployment});
cluster-level throughput and behavior under skewed (hot-tenant) traffic remain
to be evaluated.

\paragraph{Evaluation scope.}
Accuracy is averaged over 10 random seeds (Tables~\ref{tab:accuracy}
and~\ref{tab:accuracy_bge}); the
remaining per-seed variance is non-trivial on the smaller few-shot tasks. The
\sysname{} serving sweeps report the mean over \SweepNumSeeds{} seeded runs
per configuration; the PEFT baselines are single runs, adequate for the large
multiplicative gaps ($\geq$\SpeedupMixedMin$\times$ on mixed-tenant traffic)
they support (\S\ref{sec:results_baselines}).

\section*{Ethics Statement}

This work addresses inference-time efficiency for multi-tenant NLP systems.
We identify no specific ethical concerns beyond those inherent to the
underlying models (\eg bias in pre-trained encoders).
The system is intended for legitimate multi-tenant SaaS deployments.
Adapter isolation is enforced by design: per-tenant weights are never merged
into the shared base model, eliminating cross-tenant contamination risks
present in weight-merging approaches.

\section{Horizontal Deployment}
\label{sec:deployment}

Our measurements isolate a single GPU node; this appendix describes how the
same serving primitive composes into a horizontally scaled cluster. We provide
a reference deployment---Kubernetes manifests and a FastAPI serving layer---that
is intentionally minimal: it demonstrates the architecture rather than
optimizing it, and is meant to be adapted to a given workload's batching,
autoscaling, and adapter-placement policy. We do not evaluate it empirically.

\paragraph{Stateless replicas.}
The base encoder is replicated across pods and adapters are loaded from
S3-compatible object storage, so the only per-node state is the in-GPU adapter
cache, which is reconstructible from storage. Each pod runs the dynamic batcher
and \sysname{} engine of \S\ref{sec:system} unchanged.

\paragraph{Tenant-sticky routing.}
An ingress layer routes by a consistent hash of the tenant identifier
(NGINX \texttt{upstream-hash-by} on an \texttt{X-Tenant-Id} header, mirrored by
an application-level hash ring with virtual nodes). Each tenant is thus pinned
to a single pod that holds its adapter resident in GPU memory, so the
$\mathcal{O}(1)$-in-$N$ latency we measure holds at each pod, and because the
replicas are independent, aggregate request throughput grows with the number of
pods ($\approx\!K\times$ a single node for $K$ pods). Serving more than a single
node's $\approx$\CapacityRankEight-adapter ceiling (Finding~4)
additionally requires
partitioning the adapters across pods by the same hash, so each loads only its
shard; the reference deployment instead replicates a fixed adapter set per
pod---simpler, and adequate when the population fits one node---leaving
shard-aware placement as a configuration change.

\paragraph{Elasticity and hot reload.}
A horizontal pod autoscaler adds or removes replicas on utilization metrics.
Consistent hashing remaps only $\approx\!1/K$ of tenants on a scaling event, so
disruption is bounded to those tenants, whose adapters are then (re)loaded on
their new pod from object storage. Adapter retraining is propagated by a
publish/subscribe channel (Redis) that triggers in-place reload without a pod
restart.

\paragraph{Routing caveat.}
Sticky routing pins a tenant to one pod, so a single high-traffic tenant cannot
be spread across nodes without sacrificing cache locality; cluster behavior
under skewed tenant traffic is left to future work.
